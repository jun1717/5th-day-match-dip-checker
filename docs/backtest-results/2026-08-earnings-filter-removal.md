# 記録: 決算日フィルターの削除 (2026-08-09)

`earningsFilterMode` / `data/earnings.csv` / 理由キー `earnings_soon` を**機能ごと削除**した判断の記録。

## この記録の位置づけ(A/B検証は行っていない)

`docs/backtest-results/` の他の記録と違い、**バックテストによるA/B比較を実施していない**。理由は2つ。

1. **性能仮説の検証ではない。** 決算フィルターは「成績が良くなるから」入れた機能ではなく、リスク上限の不変条件(決算ギャップで想定損失 `maxLossYen` の前提が崩れるのを防ぐ)として導入した。今回外す理由も成績ではなく、**入力データ `data/earnings.csv` を常時最新に保つ運用コストが便益を上回った**こと。判断軸が最初から採用基準(期待値R・約定数)の外にある。
2. **そもそも検証が不可能だった。** 後述のとおりフィルターが単独で判定を変えた事例は16営業日で1件。この発生ペース(年10〜20件)では2〜3四半期データを溜めても期待値Rの有意差は原理的に出ない。運用マニュアルに残していた「履歴が溜まったら `--earnings-filter off` とA/B」という予約は、**実行しても答えの出ない予約**だった。

## 判断根拠(実データ)

### 1. カバレッジが構造的に埋まらなかった

| 項目 | 値 |
|---|---|
| watchlist の銘柄数(ユニークcode) | 98 |
| `earnings.csv` に登録済みだった銘柄 | **11(11%)** |
| 未記入リスト `data/earnings_todo.md` に残っていた銘柄 | 22(対象外のETF1件を除く) |
| そもそも着手していなかった銘柄 | 65 |

登録済み11社は2026-07-18に公式IRカレンダーで直接確認できた分。`earnings_todo.md` の22銘柄は「会社が次回四半期決算日をまだ公表していない」「公式ページが403でブロックされる」「検索では前年の日付しか拾えない」といった理由で、**手を動かしても埋められなかった**もの(理由は同ファイルに記録されていた)。

つまり**89%の銘柄では、導入直後から手動確認が唯一の防御だった**。「あれば効く安全な既定」のつもりだったが、実際には「11%だけ効く」機能であり、残り89%について「ツールが見てくれている」と誤認するほうがむしろ危険だった。

### 2. 実際に判定を変えた事例は1件だけ

シグナル履歴(`data/history/signals/`)16営業日分(2026-06-05〜2026-08-07)を全走査した結果:

- `earnings_soon` が付いた候補: 延べ **44件**
- そのうち **`earnings_soon` が単独で buy_candidate を watch に降格させた事例: 1件**

| 日付 | 銘柄 | individualScore | themeScore | rewardR | 同時に付いていた理由キー |
|---|---|---|---|---|---|
| 2026-07-28 | 9503 関西電力 | 90 | 100 | 5.51 | `stop_too_tight` / `volume_not_dry` / `market_regime_weak`(いずれも `flag` = 降格させない) |

残る43件は `theme_weak` / `individual_score_low` / `ma25_broken` / `reward_r_too_low` などの理由で**すでに watch・avoid だった**候補で、フィルターの有無で判定は変わらない。

### 3. 現時点ですでに不発

`earnings.csv` の最終行は 2026-08-07 で、2026-08-09時点で**全行が過去日**。四半期ごとの追記を止めた瞬間にフィルターが静かに無効化される設計であり、実際にそうなっていた。したがって削除しても当面の判定出力は1件も変わらない。

## 失われた防御と、代替が機能する条件

**失ったもの**: 決算発表3営業日前(発表当日を含む)の買い候補を自動で watch に降格する動作。ただし恩恵を受けていたのは登録済み11銘柄だけで、実績は16営業日で1件。

**代替**: [運用マニュアル §1](../運用マニュアル.md) の決算手動確認を、条件付き(「`earnings.csv` 未登録銘柄のみ」)から**全銘柄・無条件の必須項目**に格上げした。買い候補が出たら、その銘柄に3営業日以内の決算がないかを証券会社アプリ・会社IRページで必ず確認し、あれば見送る。

代替が機能する条件は次の3つで、いずれも運用側で担保する:

1. **確認が必要なのは買い候補が出た日だけ**(候補ゼロの日は作業なし)。1日あたり0〜数銘柄なので証券会社アプリで数十秒。四半期に98銘柄を一括登録する作業より軽く、**続けられる**。
2. **チェックが判断フローに埋め込まれていること**。運用マニュアルの §1 手順3・夜の判断フロー図・§0のセットアップ状況サマリの3箇所に「全銘柄・手動確認が唯一の防御」と明記した。
3. **漏れが後から見えること**。決算翌営業日に大きなギャップで損切りされたトレードは月次レビュー(`npm run review:trades`)の実績に出る。同種の事故が繰り返されるなら、その時点で自動化を再検討する(下記)。

**この交換の本質**: 「11%の銘柄を自動で守る代わりに四半期ごとのデータ整備を負う」構成から、「100%の銘柄を手動で守る代わりにデータ整備をゼロにする」構成への移行。カバレッジは上がり、静かに劣化する部品(古い `earnings.csv`)が1つ消える。

## 運用マニュアル §大原則3 との関係

大原則3は「**ルールは思いつきで変えない。変えたくなったらバックテストでA/B → 採用基準を満たしたら変更 → 記録**」。今回はこの手順を通していないので、なぜ違反ではないのかを明示しておく。

- 大原則3が防いでいるのは「**成績が思わしくないときに、感情で判定ルールを緩める/締める**」こと。守るべき対象は `config/rules.json` の閾値やモード、すなわち**性能仮説**の部分である。
- 今回変えたのは判定の緩さ・厳しさではなく、**維持不能な入力データ(手入力の `earnings.csv`)に依存した機能を撤去する**という構成の判断。動機は成績ではなく運用コストであり、「負けたから外す」ではない(むしろ成績への影響がほぼゼロであることを上記2・3で測定済み)。
- 判断軸が異なるため採用基準(期待値R改善 かつ 約定数60%以上残存)は適用できず、A/Bの対象外とする。これは [2026-07-max-position.md](2026-07-max-position.md) で `maxPositionYen` を「性能仮説ではなく予算制約」として扱ったのと同じ整理。
- **A/Bの代わりに課した条件**は3つ: ①削除の影響を実データで測る(単独降格1件)②失われた防御の代替を運用手順に明記する(全銘柄・手動確認)③この記録を残す。

### 再導入したくなったら(蒸し返し防止)

「やっぱり決算フィルターが要る」と思ったときは、**入力データをどう維持するかを先に決めること**。手入力のCSVを四半期ごとに更新する案は**一度失敗しているので却下**(カバレッジ11%で頭打ち・残りは公式ソースが取れなかった)。手入力に依存しない入力源(決算発表日を配信するAPI・データセット)を確保できる場合にのみ再実装を検討する。成績を理由にした再導入・再削除の議論はしない。
